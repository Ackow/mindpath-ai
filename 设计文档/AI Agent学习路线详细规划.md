# AI Agent 学习路线详细规划

> 定位为《AI学习路线与知识地图》阶段 6 的 **6E：AI Agent 与应用工程** 专项。目标不是堆叠框架，而是交付一个安全、可评估、可观测的 Agent 应用：它能基于受控知识库回答问题、在明确权限下调用工具，并通过 FastAPI 提供稳定接口。

## 前置与边界

**前置能力**：完成阶段 0 的 Python、数据与工程习惯，阶段 1 的问题定义，阶段 3 的评估与可靠性；建议完成阶段 5 的 PyTorch/LLM 基础，至少理解 token、embedding、概率采样和 Transformer 的基本角色。

**建议周期**：12 周，每周 6-8 小时。若没有 GPU，可使用 API 或小型本地模型；所有项目都应记录模型、版本、成本和数据许可。

**Agent 的工作定义**：一个以 LLM 为推理组件的应用，在受控状态下组合检索、结构化输出和工具调用来完成任务。它不等同于“多轮聊天”，也不应拥有默认的文件、网络、数据库写入或支付权限。

```text
用户请求
  -> API 鉴权、限流与输入校验
  -> Agent 工作流（状态、检索、工具、模型）
  -> 引用/结构化结果/工具执行记录
  -> 评估、审计日志、反馈与监控
```

## 总览

| 阶段 | 周数 | 核心问题 | 阶段交付 |
|---|---:|---|---|
| A. LLM 应用基础 | 1-2 | 如何可靠调用模型并约束输出？ | 可测试的聊天/抽取服务 |
| B. LangChain 与检索 | 3-4 | 如何编排链路并让回答有证据？ | 带引用的 RAG 基线 |
| C. 工具与 Agent 工作流 | 5-7 | 如何让模型安全地选择并调用工具？ | 有状态、可中断的工具 Agent |
| D. FastAPI 服务化 | 8-9 | 如何把能力做成可靠 API？ | 认证、流式响应、测试齐全的服务 |
| E. 评估、观测与安全 | 10-11 | 如何证明质量、发现失败并控制风险？ | 评测集、追踪与安全测试报告 |
| F. 综合项目 | 12 | 如何交付可演示、可复现的系统？ | 知识库助手 MVP |

## A. LLM 应用基础（第 1-2 周）

### 知识点

- **模型调用契约**：messages 的角色、系统指令与用户输入的边界；上下文窗口、token、温度、top-p、最大输出、超时、重试、幂等性与成本上限。
- **提示设计**：任务目标、输入格式、输出格式、少量示例和拒答条件；提示是可版本化的应用配置，不是隐藏的“魔法文本”。
- **结构化输出**：JSON Schema、Pydantic 模型、枚举、必填字段、解析失败重试；不使用正则从自由文本猜结构化字段。
- **基础可靠性**：模型可能产生幻觉、格式错误、遗漏或不当内容；区分模型错误、检索错误、工具错误和应用代码错误。
- **异步 Python**：`async`/`await`、超时、并发限制、取消、后台任务；理解网络 I/O 任务不应阻塞 API 进程。
- **配置与密钥**：环境变量、`.env` 仅用于本地开发、密钥轮换、日志脱敏；密钥和真实用户数据绝不进入 Git/提示词示例。

### 必做任务

1. 用 Pydantic 定义“文章摘要”结构：`summary`、`key_points`、`risks`、`confidence_note`，验证模型返回；解析失败需记录原因并有限次数重试。
2. 为同一请求比较低/高 temperature，记录格式有效率、延迟、token 和成本；结论不能只看单个满意回答。
3. 实现一个 `LLMClient` 封装，支持 timeout、指数退避、请求 ID、模型配置和测试替身（mock）。

### 验收

给定固定测试输入，服务可稳定返回通过 Pydantic 验证的结果；网络失败、超时和不合法响应不会导致未处理异常或泄露密钥。

### 参考

- [Pydantic documentation](https://docs.pydantic.dev/)，用于数据模型、校验和序列化。
- [Python asyncio](https://docs.python.org/3/library/asyncio.html)，用于并发与取消的基础。
- [OpenAI API documentation](https://platform.openai.com/docs/overview)，若使用 OpenAI 模型，按官方 SDK 与结构化输出文档实现；使用其他模型时以其官方 API 文档为准。

## B. LangChain 与检索增强生成（第 3-4 周）

### 知识点

- **LangChain 的定位**：它是组件与链路编排框架，不是 Agent 质量或安全的保证。先能用普通 Python 函数实现，再使用 LCEL/Runnable 获得组合、批量、流式和追踪能力。
- **文档管道**：来源许可、加载、清洗、去重、chunking、metadata、版本/哈希、embedding、索引；chunk 大小和 overlap 是应验证的配置。
- **检索**：关键词（BM25）、向量检索、混合检索、metadata filter、top-k、重排序；检索质量与回答质量应分别评估。
- **RAG 回答约束**：仅基于上下文回答；证据不足时拒答/追问；将引用的文档 ID、标题、片段和得分随结果返回。
- **向量数据库选择**：小型项目可用本地持久化索引；生产选择需考虑数据隔离、过滤、索引更新、备份、删除和访问控制。不要因框架示例而直接引入托管服务。
- **缓存**：区分 embedding 缓存、检索缓存和完整回答缓存；缓存键必须包含模型/提示/知识库版本，并避免跨租户泄漏。

### 必做任务

1. 用本仓库学习文档建立最小语料库；记录每份文档的路径、许可/来源、哈希与入库时间。
2. 先实现关键词检索，再实现向量检索；为 20 个人工问题标注相关章节，计算 Recall@K。
3. 实现带引用的问答：无证据时输出 `insufficient_evidence`，不补写未在片段中出现的事实。
4. 比较至少两种 chunk 策略和 top-k；记录检索召回、答案引用正确率、延迟和成本。

### 验收

每个回答返回可定位的来源；评测集上的回答引用不得指向无关文档；改变知识库版本后缓存失效。能清楚说明“检索没找对”与“模型没根据证据回答”的区别。

### 参考

- [LangChain documentation](https://python.langchain.com/docs/introduction/)，重点阅读 Runnables、retrievers、structured output 与 testing，而非照抄 Agent 快速开始。
- [LangChain templates](https://github.com/langchain-ai/langchain) 与官方示例：用于阅读组件组织方式，注意核对版本对应关系。
- [Sentence Transformers](https://www.sbert.net/)，用于理解 embedding、语义搜索与 reranker。
- [RAGAS](https://docs.ragas.io/)，用于借鉴检索/回答评估维度；自动评测须结合人工抽检。

## C. 工具调用与 Agent 工作流（第 5-7 周）

### 知识点

- **工作流优先**：固定步骤优先写成确定性 workflow；只有工具选择、计划或分支确有不确定性时才使用 Agent。工具多不代表系统更智能。
- **工具契约**：每个工具有名称、Pydantic 输入 schema、最小功能描述、返回 schema、超时、幂等性、权限与错误类型；工具的说明视为 API 文档并有测试。
- **函数/工具调用**：模型只提出意图和参数，应用层校验权限、参数、业务规则并执行；模型输出绝不直接作为 shell、SQL、HTTP 写操作或文件路径执行。
- **状态与记忆**：短期状态保存本次任务的计划、工具结果、引用和用户确认；长期记忆需要用户价值、明确同意、过期与删除机制。不要把完整聊天记录无上限塞回上下文。
- **LangGraph**：节点、边、状态、条件分支、checkpoint、人工中断和恢复；适合有显式状态与可审计步骤的 Agent，不必为单一 RAG 问答引入。
- **计划与反思的边界**：计划是可观察的工作项，不需要暴露内部推理；反复自我调用会增加成本和循环风险，应设置最大步数、预算与退出条件。
- **人工在环**：涉及发送消息、修改数据、发布内容、购买或其他外部副作用时，先展示拟执行内容并取得确认；读操作也要按数据权限控制。

### 必做任务

1. 实现三个只读工具：知识库搜索、计算器、受限的天气/汇率模拟工具。每个工具有 schema、单元测试、timeout 和错误码。
2. 用纯 Python 写状态机：`classify -> retrieve -> decide -> answer`；再用 LangGraph 实现同一流程，比较可读性、状态保存和测试难度。
3. 为工具 Agent 加入最大 3 步、单请求预算、重复调用检测和“无法完成”退出结果。
4. 加入一个需要确认的模拟写入工具；未经确认时必须不执行，并留下审计事件。

### 验收

能展示一次完整执行记录：请求、选择的工具、已校验的参数、工具结果、引用和最终回答。错误工具、未知参数、无限循环和用户拒绝均有可预测的安全结果。

### 参考

- [LangGraph documentation](https://langchain-ai.github.io/langgraph/)，重点阅读 state、persistence、human-in-the-loop 和 testing。
- [Model Context Protocol specification](https://modelcontextprotocol.io/specification/)，学习工具/资源协议及客户端-服务端边界；接入第三方 MCP 前评审其权限。
- [OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/)，用于提示注入、数据泄露和过度代理权限的威胁建模。

## D. FastAPI 服务化（第 8-9 周）

### 知识点

- **FastAPI 基础**：路由、HTTP 语义、请求/响应 Pydantic 模型、依赖注入、异常处理、OpenAPI、状态码、后台任务和 lifespan。
- **接口设计**：`POST /v1/chat`、`POST /v1/evaluations`、`GET /healthz` 等明确资源；请求 ID、会话 ID、知识库版本与模型配置应可追溯。
- **流式响应**：Server-Sent Events 或等价机制；处理客户端断开、心跳、缓冲、最终引用与错误事件，不能将 token 流误认为已完成的工具操作。
- **认证与授权**：区分身份验证和资源授权；API key/JWT 的适用边界、租户/用户隔离、最小权限、限流和配额。开发环境默认不开启真实生产策略。
- **依赖与存储**：连接池、配置注入、迁移、事务与审计；选择 SQLite/PostgreSQL/对象存储前先明确规模与一致性需求。
- **测试**：unit、API、集成、契约和失败路径测试；对 LLM/网络依赖用 mock 或录制响应，避免测试不稳定且昂贵。

### 必做任务

1. 把 B/C 的功能封装为 FastAPI，定义请求、回答、引用、工具事件和错误的 Pydantic schema。
2. 提供健康检查、版本端点、请求 ID、结构化日志和统一错误响应；所有异常转为安全的客户端消息。
3. 为同步和流式两种回答写 API 测试；模拟模型超时、检索为空、工具失败和客户端取消。
4. 在本地以环境变量加载配置，使用 `.env.example` 说明必需字段但不提交真实值。

### 验收

在干净环境依据 README 启动服务并通过测试；OpenAPI 能说明接口；错误不返回堆栈、密钥、完整私有上下文或内部工具详情。

### 参考

- [FastAPI documentation](https://fastapi.tiangolo.com/)，重点学习 Pydantic、依赖注入、安全、测试、SSE/流式相关模式。
- [HTTP status codes](https://developer.mozilla.org/en-US/docs/Web/HTTP/Status)，用于建立一致的 API 错误语义。
- [pytest](https://docs.pytest.org/en/stable/) 与 [httpx](https://www.python-httpx.org/)，用于接口与异步客户端测试。

## E. 评估、观测与安全（第 10-11 周）

### 知识点

- **离线评估集**：来自真实匿名化/授权问题、边界问题、拒答问题、注入攻击和工具失败情形；保留版本、来源、标签人和预期结果。
- **评估维度**：检索 Recall@K、引用正确性、回答事实性/完整性、结构化输出有效率、工具成功率、任务完成率、延迟、token、成本与拒答质量。
- **人工评估**：定义标尺、盲评、抽样和分歧处理。LLM-as-a-judge 仅是辅助信号，需要固定提示、模型版本和人工校准。
- **可观测性**：每个请求关联 trace ID，记录模型/提示/知识库版本、检索结果 ID、工具名称/耗时/状态、token、成本和用户反馈；日志不记录密钥或不必要的原文个人数据。
- **提示注入防护**：不可信文本与系统指令分离；检索内容不能改变工具权限；工具参数白名单/Schema 校验；高风险动作人工确认；输出编码与外部数据隔离。
- **运营安全**：速率/并发/成本限制、内容和数据保留策略、删除请求、模型供应商数据政策、依赖与 MCP 服务器供应链审查、回滚与 kill switch。

### 必做任务

1. 建立至少 50 条评测样本：常规问答、无证据问题、过时信息、冲突文档、注入文本、错误工具和越权请求均需覆盖。
2. 编写评估脚本，输出按版本可比较的 JSON/CSV；每次改 chunk、提示、模型或工具前后都运行。
3. 记录一次 trace，能够从最终答案反查到模型配置、检索片段与工具结果；为日志加脱敏测试。
4. 编写威胁模型：资产、信任边界、攻击路径、现有控制、残余风险和不可接受操作；对注入、越权工具、数据外泄和拒绝服务至少各写一个测试。

### 验收

系统可量化比较版本质量，安全测试在无授权时不能访问受限内容或产生外部副作用。任何质量提升都同时报告延迟、成本和安全回归。

### 参考

- [OpenTelemetry documentation](https://opentelemetry.io/docs/)，学习 trace、span 与关联 ID 的通用模型。
- [LangSmith documentation](https://docs.smith.langchain.com/)：如使用其平台，按数据保留和隐私配置后再上传追踪；也可只采用其评估/追踪概念。
- [OWASP LLM Top 10](https://genai.owasp.org/llm-top-10/) 与 [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework)，用于安全与治理检查。

## F. 综合项目：知识库助手 MVP（第 12 周）

**目标**：为本项目的学习文档提供问答服务。它只能依据已授权文档回答，并返回章节链接/片段；必要时调用只读搜索工具。系统必须能安全拒答、可重跑评测、可追踪每次结果。

### 最小功能清单

1. 文档入库：加载、分块、metadata、哈希、索引版本和删除/重建命令。
2. 检索：关键词与向量基线；可选 rerank；返回检索证据而非只返回生成文本。
3. 问答：结构化响应含 `answer`、`citations`、`status`、`request_id`；证据不足时明确说明。
4. 工具：至少一个只读工具，带 Pydantic schema、权限检查、超时和审计日志。
5. API：FastAPI、认证占位/开发密钥、限流策略、流式或非流式端点、健康检查、OpenAPI。
6. 质量：50+ 评测样本、版本化结果、人工抽检记录、延迟/成本统计。
7. 安全：提示注入、越权、数据泄露、工具失败和循环的测试；高风险写入一律不实现或强制确认。
8. 交付：README、架构图、配置示例、测试、数据许可说明、模型/提示/知识库版本、局限和回滚方法。

### 毕业验收

- 新环境能按 README 启动、索引文档、运行测试和生成评估报告。
- 每个常规回答能展示引用；无证据问题会拒答或追问，不编造来源。
- Agent 的每次工具调用都有校验、超时、预算和审计记录；模拟写操作没有确认不会执行。
- 评测集、威胁模型和已知局限随代码交付，而非只展示 Demo。

## 学习顺序与常见误区

1. 先完成 A、B 的可靠 RAG，再做 C 的工具 Agent；不要从“自动规划、多 Agent”开始。
2. 先写普通 Python 业务函数和测试，再用 LangChain/LangGraph 编排；框架应降低重复工作，而不是遮蔽控制流。
3. FastAPI、认证、评估与安全不是上线前的补丁，应从第一个可调用接口开始存在。
4. 先优化检索、数据和问题定义，再调提示或换大模型；“模型变大”不是检索缺失和权限错误的修复方案。
5. 不把私有文档、密钥、个人数据或未审查的第三方 MCP 工具交给默认具有广泛权限的 Agent。
